# NFR Requirements — Unit 4: ご褒美候補プール

**作成日**: 2026-05-16  
**Unit**: Unit 4 — ご褒美候補プール  
**対応要件**: F5-01〜F5-05

---

## 1. パフォーマンス要件

### PERF-4-01: 日次バッチ全処理時間上限

| 項目 | 内容 |
|------|------|
| **要件** | `reward_pool_updater` は Lambda タイムアウト（300秒）以内に完了すること |
| **根拠** | ハッカソン規模での想定ユーザー数は最大50名。1ユーザーあたり最大5キーワード×5件 = 25件のAPI呼び出し + レートリミット待機 (1 req/s) で約25秒/ユーザー → 50ユーザーで約1,250秒超過リスクあり |
| **対策** | キーワード検索を直列（1req/s）ではなく小バースト（3req 後に1秒sleep）で実行。ユーザー上限50名の範囲で300秒以内を目標 |
| **超過リスク対応** | Lambda タイムアウト前にその時点の `PoolUpdateResult` を CloudWatch Logs に出力して終了（未処理ユーザーは翌日更新）|

### PERF-4-02: 楽天APIレートリミット対応

| 項目 | 内容 |
|------|------|
| **要件** | 楽天ウェブサービス無料枠のレートリミット（1リクエスト/秒）を超えないこと |
| **実装** | キーワードごとの API 呼び出し間に `time.sleep(1.0)` を挿入 |
| **根拠** | 楽天ウェブサービスAPIの利用規約: 1アプリID あたり1リクエスト/秒 |

### PERF-4-03: Secrets Manager AppID キャッシュ

| 項目 | 内容 |
|------|------|
| **要件** | Lambda 実行コンテキスト内で `RAKUTEN_APP_ID` を1回だけ Secrets Manager から取得してキャッシュする |
| **実装** | モジュールレベルの `_RAKUTEN_APP_ID: Optional[str] = None` 変数でキャッシュ。初回呼び出し時のみ取得 |
| **理由** | 50ユーザー × 5キーワード = 250回の Secrets Manager 呼び出しを防止 |

## 2. スケーラビリティ要件

### SCAL-4-01: バッチ処理ユーザー数スケーリング

| 項目 | 内容 |
|------|------|
| **現在の上限** | Lambda タイムアウト 300秒 内で最大約 **50ユーザー** |
| **設計方針** | ハッカソンスコープ（50ユーザー以内）は単一 Lambda で処理。超過した場合は SQS + 複数 Lambda 呼び出しへの移行が必要（今回は対象外） |
| **モニタリング** | `PoolUpdateResult.total_users` を CloudWatch Logs に出力し、増加傾向をモニタリング |

### SCAL-01（継承）: DynamoDB PAY_PER_REQUEST

Unit 0 設定を継承。Unit 4 では `REWARD_POOL#` の PutItem が全ユーザー分追加されるが、日次バッチのため瞬間 RCU/WCU は小さい。

## 3. セキュリティ要件

### SEC-4-01: 楽天 AppID の Secrets Manager 管理

| 項目 | 内容 |
|------|------|
| **要件** | 楽天ウェブサービスの `applicationId` は専用シークレット `ars/rakuten` に `RAKUTEN_APP_ID` フィールドとして保存する |
| **実装** | `secrets.py` の `get_secrets()` で一括取得。環境変数への平文保存禁止 |
| **根拠** | OWASP A02: Cryptographic Failures. API キーの平文保存防止 |

### SEC-4-02: 楽天APIレスポンスのパース安全性

| 項目 | 内容 |
|------|------|
| **要件** | 楽天APIレスポンスの商品名・URLは検証なしで DynamoDB に保存してよい（LINE Reply や LIFF での出力時に適切にエスケープされることを Unit 5/7 で担保する） |
| **補足** | `itemName` は100文字に切り詰めてDOS的な長大文字列を防ぐ |

### SEC-01（継承）: LINE Webhook 署名検証

Unit 4 は LINE Webhook を直接受け取らないため N/A。

### SEC-04（継承）: PII ログ保護

`user_pk`（`USER#{...}`）はログに出力可能。楽天APIレスポンスに個人情報は含まれない。

## 4. 可用性要件

### AVAIL-4-01: 楽天API障害時の既存プール維持

| 項目 | 内容 |
|------|------|
| **要件** | 楽天APIが3回リトライ後も失敗した場合、そのユーザーの `REWARD_POOL#` は **更新せず既存を維持** する |
| **実装** | 例外をキャッチ → `error_count` カウント + 警告ログ → 次ユーザーへ継続 |
| **理由** | プール更新失敗で Unit 5 の提案が壊れることを防ぐ（古い候補でも提案は可能） |

### AVAIL-01（継承）: DynamoDB 可用性

マルチAZ の DynamoDB を使用（Unit 0 設定継承）。

## 5. コスト要件

### COST-4-01: 楽天API無料枠内運用

| 項目 | 内容 |
|------|------|
| **要件** | 楽天ウェブサービスAPIの無料枠（1日1,000リクエスト以内）を超えないこと |
| **試算** | 50ユーザー × 5キーワード = 250リクエスト/日 → 無料枠の25%。余裕あり |
| **上限保護** | `reward_pool_updater.py` で総リクエスト数をカウントし、900超えでバッチを緊急停止 |

### COST-4-02: Secrets Manager 呼び出しコスト

| 項目 | 内容 |
|------|------|
| **要件** | `RAKUTEN_APP_ID` は Lambda コンテキスト内で1回のみ取得（PERF-4-03 と同一対策） |
| **試算** | 1日1回バッチ → 1呼び出し/日 → 月30回 → 無料枠内（10,000回/月） |
