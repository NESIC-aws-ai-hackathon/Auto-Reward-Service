````text
あなたは既存リポジトリ「Auto Reward Service / ARS」の開発担当AIです。

# 0. プロダクト概要

プロダクト名は Auto Reward Service、略称 ARS です。

キャラクター名は必ず **「ふれまーるちゃん」** に統一してください。

過去名や表記ゆれがある場合は置換してください。

- NG: リワードちゃん
- NG: フレマールちゃん
- OK: ふれまーるちゃん

ふれまーるちゃんは、表向きには「ざっくり余剰費の支出を管理する家計簿アプリ」の案内役です。

ただし、プロダクトの本質は単なる家計簿ではありません。

# コンセプト

「疲れたあなたに、買っていい理由を作るレコメンドサービス」

ARSは、ユーザーの支出履歴・今月の余剰費・公開ほしい物リスト・位置情報・会話履歴・疲労度などをもとに、今ちょうど買ってよさそうなものを提案します。

節約を強制するアプリではなく、ユーザーが自分の欲望を安全に、気持ちよく、少しだけ正当化できる体験を提供します。

# 重要な設計思想

ARSの主機能は「寄り道」ではありません。

寄り道は機能の一つです。

主機能は以下です。

- ざっくり余剰費の把握
- 公開ほしい物リストを使った「欲望在庫」の管理
- 買っていい理由の生成
- PWA通知による能動レコメンド
- LINEでの会話継続
- 明示承認後の購入支援
- Nova Act によるカート搬送・購入直前支援・明示承認後の購入自動化

# 1. 追加・修正したい全体像

以下のユーザー体験を実現してください。

## 基本体験

1. ユーザーがLINE公式アカウント「ふれまーるちゃん」を友だち追加する
2. LINEまたはPWAで、ざっくり支出を記録する
3. 今月の残り余剰費を確認できる
4. ユーザーが公開ほしい物リストURLを登録する
5. ARSが公開ほしい物リストを「欲望在庫」として保存する
6. ふれまーるちゃんが、余剰費・疲労度・ほしい物リスト・位置情報などからおすすめ商品や寄り道先を選ぶ
7. ふれまーるちゃんが「買っていい理由」を生成する
8. 必要に応じて Nova Act が商品ページを開き、商品を買い物かごまで運ぶ
9. PWA通知で「入れておいたよ」「今これ良さそうだよ」と通知する
10. ユーザーがLINEのリッチメニュー「ふれまーるちゃんと話す」を押す
11. 直近の通知内容からLINE会話が開始される
12. ユーザーが「いらない」と言えば、対象を取り下げる
13. ユーザーが「買って」など曖昧に言った場合は、明示承認を要求する
14. ユーザーが「この商品を購入して」と明示した場合のみ、購入処理へ進む
15. 購入処理は安全チェックを通過した場合のみ実行する
16. 購入後は支出記録に反映する

# 2. LINE公式アカウント / リッチメニュー

LINEのリッチメニューは6面構成にしてください。

## リッチメニュー構成

2行 x 3列です。

- 左上: ダッシュボード
- 上中央: ふれまーるちゃんと話す
- 右上: ふれまーるちゃんからのおすすめ
- 左下: 支出を記録
- 下中央: 今月の残り
- 右下: 設定

## 「ふれまーるちゃんと話す」の重要仕様

リッチメニューの「ふれまーるちゃんと話す」を押した時、単なる通常会話開始にしないでください。

まずバックエンドで以下を確認してください。

- 直近にPWA通知されたレコメンドがあるか
- `CART_ADDED`
- `WAITING_USER_DECISION`
- `RECOMMENDED`
- `LOCATION_RECOMMENDED`
- `NOTIFICATION_SENT`
- `PURCHASE_CONFIRMATION_REQUIRED`
- `LOGIN_REQUIRED`
- `USER_TAKEOVER_REQUIRED`

など、会話継続すべき状態があるか。

存在する場合、その通知内容・Recommendation状態・CartAutomationJob状態から会話を開始してください。

例:

```text
ふれまーるちゃん:
さっき通知したやつですね。

ほしい物リストで熟成していた入浴剤、
今のあなたにちょうどよさそうだったから、
買い物かごに入れておいたよ～！

買うって言ったら買っちゃうけど、どうする？
```

状態がない場合は通常会話を開始してください。

# 3. PWA通知 / 通知一覧

PWA側に、ふれまーるちゃんからの通知が並ぶチャット風UIを追加してください。

## PWA通知の用途

PWA通知は、LINE push通知の代替・補完です。

通知をタップすると、PWA内の通知詳細に遷移します。

通知詳細から以下ができるようにしてください。

- LINEで話す
- 対象レコメンドを見る
- 寄り道レーンを見る
- 店舗詳細を見る
- 商品詳細を見る
- カート状況を見る
- Nova Act の処理状況を見る
- Amazonログインが必要な場合はユーザー操作へ進む
- 購入直前確認画面を見る

LINE PUSH機能を使っているものはすべて廃止してください。

## 通知内容例

```text
ふれまーるちゃん:
ほしい物リストで熟成していた入浴剤、
今のあなたにちょうどよさそうだったので、
買い物かごに入れておいたよ～。

疲れているんだもん仕方ないよね！

買うって言ってくれたら買っちゃうよ！
```

PWA通知そのものから直接LINE会話を開始できない場合でも、以下の状態をバックエンドに保存してください。

- userId
- notificationId
- recommendationId
- notificationType
- messageText
- status
- createdAt
- expiresAt

その後、ユーザーがLINEリッチメニュー「ふれまーるちゃんと話す」を押した時に、最新の有効な通知を見つけ、その内容から会話開始してください。

# 5. 公開ほしい物リスト連携 / 欲望在庫

今の段階では、Amazonログイン起点にはしません。

まずは **公開ほしい物リストURL登録** を起点にしてください。

## 基本方針

- ユーザーが公開ほしい物リストURLを登録する
- ARSが公開ページから商品情報を取得する
- 商品を「欲望在庫」として保存する
- レコメンドの主ソースにする
- Amazon ID / パスワードは要求しない
- ほしい物リスト取得にログインセッションを使わない

## API案

```http
POST /wishlist/public-url
```

入力:

```json
{
  "userId": "string",
  "wishlistUrl": "string",
  "displayName": "string optional"
}
```

処理:

1. URL形式を検証する
2. 公開ページとしてアクセスできるか確認する
3. 商品一覧を取得する
4. 商品候補として保存する
5. 同期結果を返す

既存DB設計に合わせてください。

# 6. レコメンド生成

ふれまーるちゃんは以下の情報からおすすめを選んでください。

- 今月の残り余剰費
- ご褒美枠
- 支出履歴
- 公開ほしい物リスト
- 欲望熟成日数
- ユーザーの会話履歴
- 疲労度
- 時間帯
- 位置情報
- 過去の拒否履歴
- 購入履歴

## レコメンド対象

最優先は `WishlistItem.status === "ACTIVE"` の商品です。

優先順位:

1. ACTIVEなWishlistItem
2. desireAgingDaysが長い
3. 価格が購入上限以下
4. 余剰費に収まる
5. 過去にDECLINEDされていない
6. 疲労度・時間帯に合う
7. 商品URLが有効
8. 在庫がある

## 買っていい理由生成

Bedrock / LLM / 既存AI機能がある場合は利用してください。

例をふれまーるちゃんの緩い口調で生成してください。

```text
この商品は、ほしい物リストに入ってから17日目です。
衝動買いではなく、すでに熟成した欲望です。

今日は疲労度も高く、今月のご褒美枠にも収まっています。
これは浪費ではなく、明日の自分を守るための保守費です。
```

## 注意

AIが生成する文面はキャラクター性を出してよいですが、金額・商品名・購入可否などの重要情報はルールベースでチェックしてください。

# 7. ふれまーる・カート搬送

機能名:

```text
ふれまーる・カート搬送
```

これは、ふれまーるちゃんがレコメンドした商品を買い物かごまで運ぶ機能です。

## 重要

購入確定は、ユーザーが明示的に承認した場合のみ実行してください。

曖昧な発話では購入しないでください。

## 状態遷移

レコメンド単位で状態管理してください。

```text
RECOMMENDED
CART_ADDING
CART_ADDED
WAITING_USER_DECISION
DECLINED
CART_REMOVING
REMOVED_FROM_CART
PURCHASE_CONFIRMATION_REQUIRED
PURCHASE_APPROVED
PURCHASING
PURCHASED
PURCHASE_SIMULATED
PURCHASE_FAILED
CANCELLED
ERROR
```

## カート投入通知

カート投入が成功したらPWA通知を送ります。

```text
ふれまーるちゃん:
ほしい物リストで熟成していた {productTitle}、
今のあなたにちょうどよさそうだったから、
買い物かごに入れておいたよ～！

{reasonText}

買うって言ったら買っちゃうけど、どうする？
```

## ユーザーが「いらない」と言った場合

以下は拒否として扱ってください。

```text
いらない
やめる
買わない
戻して
カートから出して
今回はなし
まだいい
熟成させる
```

処理:

1. 状態を `DECLINED` または `CART_REMOVING` にする
2. カートから削除する
3. `REMOVED_FROM_CART` にする
4. 欲望在庫へ戻す

返答例:

```text
わかりました。
かごから出して、欲望熟成庫に戻しておきます。
また必要そうな日に持ってきますね。
```

## ユーザーが曖昧に購入意思を示した場合

以下は購入確定として扱わないでください。

```text
買って
お願い
いいよ
OK
はい
任せる
欲しい
買いたい
それで
おすすめなら
すすめて
買っちゃおう
```

処理:

1. 状態を `PURCHASE_CONFIRMATION_REQUIRED` にする
2. 明示的な言い直しを要求する

返答例:

```text
買いたい気持ちはわかったよ！
購入するってことね！

それじゃあ、もう一度
「この商品を購入して」
と送ってくれたら、買ってくるよ～～
```

## 明示購入として扱う発話

以下のみ購入承認として扱ってください。

```text
この商品を購入して
この内容で購入して
注文を確定して
この商品を注文して
はい、購入を確定します
{商品名}を購入して
```

処理:

1. 状態を `PURCHASE_APPROVED` にする
2. 安全チェックを実行する
3. 問題なければ購入処理へ進む

返答例:

```text
承認を確認しました。
購入処理に進みます。
```

# 8. 購入処理の安全要件

本物の購入処理は危険なので、デフォルトでは無効にしてください。

環境変数で制御してください。

```env
CART_AUTOMATION_MODE=stub
ENABLE_REAL_PURCHASE=false
NOVA_ACT_DEMO_MODE=true
MAX_PURCHASE_AMOUNT=1000
```

## デフォルト

```text
CART_AUTOMATION_MODE=stub
ENABLE_REAL_PURCHASE=false
NOVA_ACT_DEMO_MODE=true
MAX_PURCHASE_AMOUNT=1000
```

本物の購入確定に進むのは、以下を満たす場合のみです。

- `ENABLE_REAL_PURCHASE=true`
- 状態が `PURCHASE_APPROVED`
- 明示承認テキストが保存されている
- 金額が上限以下
- 数量が1
- 定期便ではない
- 支払い方法を変更していない
- 配送先を変更していない
- 対象商品が現在のrecommendationIdと一致している
- Nova Act が注文確認画面で対象商品・数量・金額を検証できている

## 絶対NG

- ユーザーの明示承認なしに購入する
- 「買って」だけで購入する
- Amazon ID / パスワードを保存する
- Cookieやセッション情報をログに出す
- 支払い方法を変更する
- 配送先を変更する
- 数量を勝手に増やす
- 定期便をONにする
- CAPTCHA / MFAを自動突破しようとする
- 高額商品を勝手に対象にする
- 認証画面、支払い画面、住所画面のスクリーンショットを保存する

# 10. Nova Act を使ったカート搬送 / 購入自動化方針

ARSの「ふれまーる・カート搬送」は、最終的に Nova Act を使ってブラウザ操作を自動化する方針です。

ここが本機能の中で最も難しい部分です。

そのため、単なる stub では終わらせず、以下を必ず実装してください。

- `NovaActCartAutomationWorker` の skeleton
- 実行モード切り替え
- 非同期ジョブ化
- ログイン要求検知
- MFA / CAPTCHA 検知
- Human in the Loop / User Takeover 前提の状態管理
- 商品名・価格・数量・定期便チェック
- 購入直前チェック
- 証跡保存
- エラー分類
- stub / hybrid fallback

## Nova Act の位置づけ

Nova Act は以下の操作に利用します。

- Amazonの商品ページを開く
- 商品ページの内容を確認する
- 数量が1であることを確認する
- 定期便ではないことを確認する
- 商品をカートに入れる
- カート内の商品を削除する
- 注文確認画面を確認する
- ユーザーが明示承認した場合のみ、注文確定へ進む
- 注文完了後、注文番号や完了状態を取得する

Nova Act は以下には使わないでください。

- 公開ほしい物リストの初回取得
- Amazon ID / パスワードの保存
- MFA / CAPTCHA の自動突破
- 支払い方法の変更
- 配送先の変更
- 数量の勝手な変更
- 定期便の有効化
- ユーザーの明示承認なしの購入確定

公開ほしい物リストの取得は、まず `AmazonPublicWishlistProvider` または `DemoProductProvider` で行ってください。

Nova Act は、あくまで「商品ページ以降のカート搬送・購入支援」に使います。

# 11. Nova Act 実装アーキテクチャ

Nova Act は通常の同期API処理に直接組み込まないでください。

カート投入・削除・購入処理は時間がかかり、ログイン・MFA・CAPTCHA・画面遷移失敗が発生する可能性があります。

そのため、以下のように非同期ジョブとして扱ってください。

```text
LINE / PWA / API
  ↓

# 13. Amazonログイン / Human in the Loop 方針

Amazonログインが必要になった場合、Nova Act が自動でIDやパスワードを入力する実装にはしないでください。

ログインが必要な場合は、状態を `LOGIN_REQUIRED` または `USER_TAKEOVER_REQUIRED` にして、ユーザー本人にブラウザ操作を引き渡してください。

## ログインの流れ

```text
Nova Act がAmazon商品ページを開く
  ↓
ログインが必要な画面を検知
  ↓
CartAutomationJob.status = LOGIN_REQUIRED
  ↓
PWAに「Amazonログインが必要です」と表示
  ↓
ユーザーが自分でログインする
  ↓
MFAやCAPTCHAもユーザーが対応する
  ↓
ログイン完了後、Nova Act が処理を再開する
```

## ユーザー向け文言例

```text
ふれまーるちゃん:
Amazonに入るところだけ、あなたの手が必要です。

パスワードや認証コードは、ふれまーるちゃんには教えなくて大丈夫だよ。
ログインできたら、買い物かごまで運ぶね。
```

## MFA / CAPTCHA

MFA / CAPTCHA が出た場合は、必ず人間に操作を返してください。

以下の状態を使ってください。

- `MFA_REQUIRED`
- `CAPTCHA_REQUIRED`
- `USER_TAKEOVER_REQUIRED`

絶対にMFAやCAPTCHAを自動突破しようとしないでください。

# 14. Nova Act デモ方針

ハッカソンデモでは、Nova Act を使った本物のブラウザ操作を見せたいです。

ただし、失敗時にデモ全体が止まらないように、以下の3モードを用意してください。

```env
CART_AUTOMATION_MODE=stub | nova_act | hybrid
ENABLE_REAL_PURCHASE=false | true
NOVA_ACT_DEMO_MODE=true | false
MAX_PURCHASE_AMOUNT=1000
```

## stub mode

実ブラウザ操作はしません。

- addToCart → 即 `CART_ADDED`
- removeFromCart → 即 `REMOVED_FROM_CART`
- purchase → `PURCHASE_SIMULATED`

デモの保険として必ず残してください。

## nova_act mode

Nova Act で実ブラウザを操作します。

- 商品ページを開く
- カート投入
- カート削除
- 明示承認後の購入確定

ただし、`ENABLE_REAL_PURCHASE=false` の場合は、購入確定ボタンは押さず、購入直前で停止してください。

## hybrid mode

通常は Nova Act を使いますが、以下の場合は stub にフォールバックします。

- Nova Act の起動失敗
- ログイン未完了
- MFA / CAPTCHA でデモ継続困難
- Amazon画面構造の変化
- 商品ページ取得失敗
- 購入直前検証NG
- タイムアウト

フォールバックした場合は、必ず状態とログに残してください。

```ts
type AutomationFallbackReason =
  | "NOVA_ACT_START_FAILED"
  | "LOGIN_NOT_READY"
  | "MFA_OR_CAPTCHA_REQUIRED"
  | "PAGE_STRUCTURE_CHANGED"
  | "PRODUCT_PAGE_FAILED"
  | "SAFETY_CHECK_FAILED"
  | "TIMEOUT";
```

# 15. Nova Act による購入確定の実行条件

Nova Act が購入確定ボタンを押してよいのは、以下の条件をすべて満たす場合だけです。

- `ENABLE_REAL_PURCHASE=true`
- `CART_AUTOMATION_MODE=nova_act` または `hybrid`
- Recommendation.status が `PURCHASE_APPROVED`
- CartAutomationJob.action が `PURCHASE`
- explicitApprovalText が保存されている
- explicitApprovalText が明示購入文として判定済み
- productUrl が対象Recommendationと一致している
- 商品名が想定商品と大きくズレていない
- price <= maxAllowedPrice
- quantity === 1
- 定期便ではない
- 送料や手数料込みの合計が上限を超えていない
- 支払い方法を変更していない
- 配送先を変更していない
- 画面上で注文確定直前であることを検証できている
- `validateBeforePurchase` が ok である

どれか一つでも満たさない場合は、購入確定してはいけません。

状態を `PURCHASE_FAILED` または `ERROR` にし、理由を保存してください。

# 16. Nova Act 実行前後の安全チェック

Nova Act 実行前、商品ページ表示後、購入直前の3段階でチェックしてください。

## 実行前チェック

- recommendationId が存在する
- status が期待状態である
- productUrl が存在する
- maxAllowedPrice が設定されている
- quantity が1である
- `ENABLE_REAL_PURCHASE` の値を確認する
- `CART_AUTOMATION_MODE` の値を確認する

## 商品ページチェック

- 商品タイトル
- 価格
- 在庫状態
- 定期便ではないこと
- 数量
- 販売ページが想定URLまたは想定ドメインであること

## 購入直前チェック

- 商品名
- 数量
- 合計金額
- 配送先を変更していないこと
- 支払い方法を変更していないこと
- 定期便ではないこと
- 明示承認済みであること
- `validateBeforePurchase` が ok であること

# 17. Nova Act 証跡保存

Nova Act 操作の結果は、デバッグとデモ検証のために証跡を保存してください。

ただし、個人情報・認証情報・支払い情報は保存しないでください。

保存してよいもの:

- 商品ページのURL
- 商品名
- 価格
- カート投入成功/失敗
- 購入成功/失敗
- 注文番号、取得できる場合のみ
- 画面スクリーンショット、ただし個人情報をマスクしたもの
- エラー種別
- 実行時間

保存してはいけないもの:

- Amazon ID
- パスワード
- Cookie
- セッション情報
- クレジットカード番号
- 詳細住所
- 氏名
- 電話番号
- MFAコード
- CAPTCHA画像
- 認証画面のスクリーンショット

## Screenshot Sanitizer

証跡スクリーンショットを保存する場合は、可能な範囲でマスク処理を入れてください。

```ts
type EvidenceScreenshot = {
  screenshotKey: string;
  sanitized: boolean;
  containsSensitiveData: boolean;
  createdAt: string;
};
```

`containsSensitiveData=true` の場合は保存しない、または即削除してください。

# 18. Nova Act 用プロンプト / 操作指示の作り方

Nova Act に渡す操作指示は、曖昧にしないでください。

悪い例:

```text
この商品を買って
```

良い例:

```text
Open the product URL.
Verify the product title and price.
Set quantity to 1.
Do not enable subscription.
Do not change payment method.
Do not change shipping address.
Add the item to the cart.
Stop before purchase confirmation unless purchaseApproved is true.
If login, MFA, or CAPTCHA is required, stop and return USER_TAKEOVER_REQUIRED.
```

購入時も、必ず制約を明記してください。

```text
Open the cart or checkout page.
Verify that the item matches the expected product title.
Verify quantity is exactly 1.
Verify total price is less than or equal to maxAllowedPrice.
Verify subscription is not enabled.
Do not change payment method.
Do not change shipping address.
If any verification fails, stop.
Only confirm the order if purchaseApproved is true and explicitApprovalText is valid.
After confirming, capture the order confirmation status and order id if visible.
```

# 19. Nova Act 実装優先順位

Nova Act 周りは難しいため、以下の順で実装してください。

## Step 1: Stub Worker 完成

- `CartAutomationWorker` interface
- `StubCartAutomationWorker`
- 状態遷移
- 通知
- 意図判定
- 安全チェック
- テスト

## Step 2: Nova Act Skeleton

- `NovaActCartAutomationWorker` クラスを追加
- 設定値・ジョブ・戻り値・エラー分類を先に固める
- この段階では実操作なしでもよい

## Step 3: Add to Cart のみ実装

最初に実装するNova Act操作は `addToCart` だけにしてください。

- 商品ページを開く
- 商品名・価格確認
- 数量1確認
- 定期便ではないこと確認
- カート投入
- `CART_ADDED` に更新
- PWA通知

## Step 4: Remove from Cart 実装

次に `removeFromCart` を実装してください。

- 対象商品をカートから削除
- 失敗しても購入には進まない
- `REMOVED_FROM_CART` または `FAILED`

## Step 5: Purchase直前停止

`ENABLE_REAL_PURCHASE=false` で、購入直前まで進んで停止する実装をしてください。

- 注文確認画面に到達
- 商品名・金額・数量を検証
- 購入確定ボタンは押さない
- `PURCHASE_SIMULATED` または `READY_TO_PURCHASE` にする

## Step 6: Real Purchase

最後に、`ENABLE_REAL_PURCHASE=true` の場合のみ購入確定を実装してください。

- 明示承認済み
- 安全チェックOK
- 上限金額以下
- 数量1
- 定期便なし
- 支払い方法変更なし
- 配送先変更なし
- 注文確認画面検証OK

この条件を満たす場合のみ注文確定してください。

# 20. 意図判定

以下の関数を実装してください。

```ts
type PurchaseIntent =
  | "DECLINE"
  | "AMBIGUOUS_BUY"
  | "EXPLICIT_PURCHASE"
  | "OTHER";

function classifyPurchaseIntent(message: string, productTitle?: string): PurchaseIntent;
```

ルール:

- 「いらない」「買わない」「戻して」「カートから出して」などは `DECLINE`
- 「買って」「お願い」「OK」「いいよ」「欲しい」などは `AMBIGUOUS_BUY`

LLM判定を使っても構いませんが、購入可否の最終判定は必ずルールベースでガードしてください。

# 31. 実装時の注意

特に購入系の機能は、必ず安全側に倒してください。

このサービスは「勝手に購入するサービス」ではありません。

「ふれまーるちゃんが、買っていい理由を作り、商品をかごまで運ぶ。
ただし購入確定は、ユーザーが明示的に『この商品を購入して』と承認した場合のみ実行する」

というサービスです。

ただし、Nova Act に責任を委ねすぎないでください。

購入可否・金額上限・数量・定期便・配送先・支払い方法・明示承認は、必ずアプリケーション側のルールベースで検証してください。
````
