# Auto-Reward-Service 要件整理

## 背景

Auto-Reward-Service (ARS) は、AWS AI-DLC ハッカソン向けの「ご褒美支援サービス」である。

中核体験は、ユーザーが **PWA上でふれまーるちゃんとテキスト・音声で会話すること** である。

ユーザーはPWAチャットで話すだけで、収入・固定費・支出・好み・疲れ・ご褒美履歴が自然に蓄積されていく。
その情報をもとに、ふれまーるちゃんが「買っていい理由」を提示する。

> **頑張ったあなたに、ちょっとだけご褒美を。
> 話すだけで家計簿になり、好きなものを覚えてくれる、頑張りすぎない家計簿アプリ。**

# 0. 最重要方針

## 全体像

```text
PWA（メインUI・唯一のフロントエンド）
  - テキストチャット（ふれまーるちゃんとの会話）
  - 音声チャット（Nova Sonic リアルタイム）
  - オンボーディング（収入・固定費・予算計算）
  - 支出登録（会話の副作用として自然に抽出）
  - ご褒美相談・提案
  - 購入確認
  - ダッシュボード（予算残高・ストレス・支出）
  - 回復提案（ストレスに応じた無料＋有料オプション）
  - 日記（自動生成）
  - Web Push通知
  - 設定
  - ヘルスケア連携（ショートカット経由）

外部API
  - 楽天API: 商品候補取得（実装済み）
  - ホットペッパーAPI: 飲食店・外食ご褒美候補取得（実装済み）
  - Amazon公開ほしい物リスト: URL登録→スクレイピング→候補化（実装済み）

認証
  - Cognito（email + パスワード）
  - ユーザー上限7名（ハッカソンMVP）
```

```text
技術スタック:
- フロントエンド: Vite + React 19 + TypeScript 5.7 (PWA)
- バックエンド: AWS SAM (Python 3.13, Lambda)
- AI: Amazon Bedrock (Claude Haiku 4.5 推論プロファイル) + Nova Sonic v2
- DB: DynamoDB (シングルテーブル設計)
- 通知: Web Push (VAPID)
- 配信: CloudFront + S3
- 音声: WebSocket API Gateway + Nova Sonic
- 認証: Amazon Cognito User Pool
```

# 1. PWAチャットの会話状態管理を強化する

## 問題

現在、チャットの各会話が単発処理になっており、ユーザーの次の発話が「何の続きか」として扱われていない。

その結果、以下が起きている。

```text
ふれまーるちゃんが質問する
↓
ユーザーが答える
↓
文脈が消える（バックエンド側で）
↓
無関係な雑談や別フローに流れる
```

## 修正方針

PWAチャットのすべての会話は `CONVERSATION_STATE#CURRENT` を中心に処理する。

```json
{
  "PK": "USER#{userId}",
  "SK": "CONVERSATION_STATE#CURRENT",
  "entityType": "CONVERSATION_STATE",
  "current_flow": "ONBOARDING",
  "step": "WAITING_INCOME",
  "expected_input": "amount",
  "context": {
    "last_question": "毎月の手取り収入を教えてね",
    "last_suggestion": null,
    "source": "pwa_chat"
  },
  "expires_at": 1760000000
}
```

想定する flow:

```text
ONBOARDING
TALK
EXPENSE_ENTRY
EXPENSE_CONFIRM
REWARD_PROPOSAL
PURCHASE_CONFIRM
NONE
```

チャットメッセージ処理順序は以下に固定する。

```text
1. userId を取得（Cognito sub）
2. CONVERSATION_STATE#CURRENT を取得
3. 状態中なら、そのフローを最優先で処理
4. 状態がなければ intent 分類
5. 支出・嗜好・感情を副作用として抽出
6. 必要に応じてご褒美候補を取得
7. 最後にふれまーるちゃん口調で返信
```

# 2. PWAナビゲーションを会話起点にする

## 問題

ボトムナビゲーションが単なるページ遷移になっている。
チャットに戻ったときに文脈が失われている可能性がある。

## 修正方針

各ナビゲーションアクションで `CONVERSATION_STATE#CURRENT` を意識する。

### チャットタブ（メイン）

```text
→ current_flow に応じた会話を継続
→ 状態がなければ自由会話（TALK）
```

### 回復タブ

```text
→ ストレスレベルに応じた回復提案を表示
→ 「これにする」で PURCHASE_CONFIRM 状態へ
```

### ダッシュボードタブ

```text
→ 予算残高・支出を確認
→ ふれまーるちゃんのコメント付き
```

## 会話の例

### 自由会話

```text
ふれまーるちゃん：
最近ちょっとハマってるものある？
甘いものでも、飲み物でも、ゲームでもなんでもいいよ♪

ユーザー：
抹茶プリンかな

処理:
- PREF_MEMORY# に「抹茶」「プリン」を保存
- 次の返答で自然に話題を広げる
```

### 支出報告

```text
ふれまーるちゃん：
今日買ったものをそのまま教えて♪
「コーヒー150円買った」みたいな感じでOK〜。

ユーザー：
コーヒー150円買った

処理:
- EXPENSE# 保存
- MONTHLY_SUMMARY# 更新
- 状態完了
```

### ご褒美相談

```text
ふれまーるちゃん：
今日はどんな感じで甘やかされたい？
甘いもの、休憩、癒し、何も考えたくない系、どれでもいいよ♪

ユーザー：
甘いもの食べたい

処理:
- PREF_MEMORY# と REWARD_POOL# を参照
- 楽天API候補も必要に応じて利用
- 候補提案
- PURCHASE_CONFIRM 状態へ
```
今日買ったものをそのまま教えて。
「コーヒー150円買った」みたいな感じでOK。

ユーザー：
コーヒー150円買った

処理:
- EXPENSE# 保存
- MONTHLY_SUMMARY# 更新

```

### ご褒美相談

```text

```

例:

```text

# 4. 支出登録後に無関係な会話へ流れないようにする

## 問題

支出処理後に通常チャットフローへ落ち、無関係な会話が始まる。

## 修正方針

支出処理後は適切な返答をして処理を終了する。

```python
if intent == "EXPENSE":
    expense_data = extract_expense(text, user_id)

    if expense_data:
        save_expense(expense_data)
        update_monthly_summary(user_id, expense_data)
        append_preference_side_effects(text, expense_data)

        reply = generate_expense_reply(expense_data)
        return {"reply": reply}
```

支出処理後の返答例:

```text
ふれまーるちゃん：
コーヒー150円、記録したよ☕
今月あと7,700円くらいご褒美枠残ってるからね♪
```

## 修正方針

```json

  "current_flow": "PURCHASE_CONFIRM",
  "step": "WAITING_PURCHASE_RESULT",
  "expected_input": "purchase_confirmation",

      "url": "...",
      "image_url": "..."

  }
}
```

以下の発話は購入確定として扱う。

```text

保存するデータ:

```text

# 7. 音声チャット（Nova Sonic）

## 方針

テキストだけでなく、音声でもふれまーるちゃんと会話できる。
WebSocket経由でNova Sonicによるリアルタイム音声会話を実現する。

## 現在の実装（維持）

- WebSocket API Gateway
- VoiceGatewayFunction (Lambda 512MB, 300s timeout)
- Nova Sonic (`amazon.nova-2-sonic-v1:0`)
- フロントエンドの音声入力UI（マイクボタン）
- 音声セッションの開始/終了

## 音声会話の副作用

音声会話もテキストチャットと同様に、以下を副作用として抽出する。

```text
- 支出（「コーヒー買った」→ EXPENSE#）
- 嗜好（「抹茶好き」→ PREF_MEMORY#）
- 感情（「疲れた」→ ストレスレベル更新）
```

音声セッション終了時にトランスクリプトを非同期分析キューに送る（現在実装済み）。

# 8. 回復提案とご褒美提案の連携

## 方針

ストレスが高いとき、回復提案 → ご褒美提案の流れを自然にする。

## 現在の実装（RecoveryService）

- ストレスレベルに応じた無料回復オプション（light/moderate/strong）
- 有料回復オプション（スイーツ、カフェ、入浴剤等）
- ふれまーるちゃん口調への変換（Bedrock）
- 許可（permit）/ スキップ（skip）の記録

## 改善: 有料回復→商品検索の連携

有料回復オプションを選択した場合、楽天APIで具体的な商品候補を検索する。

```text
ふれまーるちゃん：
コンビニスイーツもいいけど、こんなのもあるよ♪
[抹茶プリン 540円 - 楽天]
[宇治抹茶ロールケーキ 1,200円 - 楽天]

買ってみる？ それとも今日はコンビニで充分？
```

選んだ場合:
- PURCHASE_CONFIRM 状態へ
- 商品URL表示
- 「買った」で記録

# 9. 外部API統合（楽天API・ホットペッパーAPI）

## 背景

ユーザーがPWA上でふれまーるちゃんと会話しながら蓄積した好み・予算情報をもとに、
外部APIで商品・飲食店候補を探し、「買っていい理由」「行っていい理由」を提示する。

## 重要方針

### やること

- 楽天APIで商品候補を取得する（実装済み）
- ホットペッパーAPIで飲食店・ご褒美外食候補を取得する（追加実装）
- 候補を共通の `RewardCandidate` 形式に正規化する
- 候補を `REWARD_POOL#` に保存する
- チャットまたは回復提案画面で候補表示

### やらないこと

- 決済代行
- 自動購入
- カート投入

## RewardCandidate 共通Schema

```json
{
  "candidate_id": "string",
  "name": "抹茶プリン",
  "description": "疲れた日の小さなご褒美に合うスイーツ",
  "amount": 320,
  "currency": "JPY",
  "image_url": "https://...",
  "url": "https://...",
  "source": "rakuten|hotpepper|amazon_wishlist|static",
  "shop_name": "string",
  "category": "スイーツ",
  "tags": ["抹茶", "プリン", "スイーツ"],
  "reward_type": "product|restaurant|experience",
  "confidence": 0.82,
  "reason": "今月のご褒美枠に収まり、過去の好みに合うため"
}
```

## 楽天API（実装済み）

```text
u8/backend/services/product_search.py
```

- 楽天商品検索API
- キーワード・カテゴリ・価格上限で検索
- モック対応あり（APIキーなし時）
- 環境変数: `RAKUTEN_APP_ID`

## ホットペッパーAPI（実装済み）

```text
u8/backend/services/hotpepper_service.py
```

- ホットペッパーグルメAPI（リクルート）
- キーワード・ジャンル・予算・位置情報で検索
- モック対応あり（APIキーなし時）
- 環境変数: `HOTPEPPER_API_KEY`
- APIエンドポイント: `GET /api/search/restaurants?keyword=&genre=&budget_max=`

注意:
- 価格は予算目安として扱う
- 「行く」「予約する」と表現する（「購入」ではない）

## Amazon公開ほしい物リスト（実装済み）

# 10. ご褒美提案ロジックを4層に分ける

## 方針

LLMに判断を丸投げしない。

```text
1. 状態推定
2. 余裕額判定
3. 候補選択
4. ふれまーるちゃん口調への変換
```

## 1. 状態推定

入力:

```text
- PWAチャットでのユーザー発話
- LIFE_LOG#
- EXPENSE#
- PREF_MEMORY#
- STRESS_SUMMARY#
- 時間帯
- 曜日
```

出力:

```json
{
  "fatigue": 0.8,
  "stress": 0.6,
  "wants_sweets": true,
  "preferred_tags": ["抹茶", "プリン", "スイーツ"]
}
```

## 2. 余裕額判定

入力:

```text
PROFILE#.income
PROFILE#.fixed_costs
PROFILE#.reward_budget_monthly
MONTHLY_SUMMARY#
```

出力:

```json
{
  "monthly_reward_budget": 12000,
  "used": 4300,
  "remaining": 7700,
  "max_recommended_amount": 800
}
```

## 3. 候補選択

候補源:

```text
WISHLIST_ITEM# (Amazon公開ほしい物リスト・最優先)
REWARD_POOL# (キャッシュ)
楽天API
ホットペッパーAPI
Static候補（RecoveryServiceの有料オプション）
```

選択条件:

```text
- 予算内
- 好みに近い
- 今の状態に合う
- 最近買いすぎていない
- 価格が軽い
```

## 4. キャラ表現

最後だけLLMに任せる。

```text
判断はコード
表現はLLM（ふれまーるちゃん口調変換）
```

# 11. 嗜好・感情・支出を全発話から副作用として拾う

## 方針

すべてのチャット発話に対して、以下を副作用として抽出する。

```text
- 支出
- 好きなもの
- 嫌いなもの
- 疲れ
- ストレス
- 空腹
- 満足
- 後悔
```

## 現在の実装（AnalysisService）

現在は非同期分析（SQSキュー経由）で以下を抽出している:
- 出来事 (LIFE_LOG#)
- 支出 (EXPENSE#)
- ストレスサマリー (STRESS_SUMMARY#)

## 追加実装: 嗜好抽出

保存方針:

```text
明確な支出 → EXPENSE# に保存（現在実装済み）

# 最終設計思想

ARSの中心は **PWA上のふれまーるちゃんとの会話**。

```text
PWAでふれまーるちゃんと会話する（テキスト or 音声）
↓
収入・固定費・支出・好み・疲れが自然に蓄積される
↓
楽天API / キャッシュから候補を取得する
↓
予算と好みに合うご褒美を選ぶ
↓
ふれまーるちゃんが「買っていい理由」を返す
↓
買ったらご褒美費として記録する
↓
Web Pushでふれまーるちゃんから話しかける
↓
またPWAで会話する
```

修正の優先順位:

```text
1. テキストチャットの応答が正常に動くこと
2. 音声チャットが開始〜終了まで動くこと
3. 会話状態管理（文脈維持）
4. 支出・嗜好の副作用抽出
5. ご褒美提案と購入確定の連携
6. 回復提案・ダッシュボード
7. Web Push通知
8. 楽天API商品検索
9. 日記・ヘルスケア連携
```

これで、ARSは「LINEから移行しきれていない状態」から、
**PWAチャット体験を中心に、音声・通知・外部APIが支える一貫した構造**になる。
