了解。前提はこうですね。

```text
主役：LINE Bot
補助：PWA
目的：PWAはWeb Push通知を受けるための受け皿
廃止：LINE Push通知
```

# Auto-Reward-Service 品質向上・LINE Bot中心・PWA Push対応・Nova Act安定化指示

## 背景

Auto-Reward-Service は、AWS AI-DLC ハッカソン向けの「ご褒美支援サービス」である。

中核体験は、ユーザーが **LINE Bot上でリワードちゃんと会話すること** である。

ユーザーはLINE Botで会話しながら、収入・固定費・支出・好み・疲れ・ご褒美履歴を自然に登録していく。
その情報をもとに、リワードちゃんが「買っていい理由」を提示する。

PWAはLINE Botの代替ではない。
PWAは主に **Web Push通知を受け取るための補助導線** として利用する。

# 0. 最重要方針

## 正しい全体像

```text
LINE Bot
  - メインの会話UI
  - オンボーディング
  - 支出登録
  - ご褒美相談
  - 購入報告
  - リワードちゃんとの会話

PWA
  - Web Push通知の購読
  - 通知許可
  - 通知クリック時の復帰先
  - Web Push診断
  - 必要に応じた補助画面

外部API
  - 楽天API: 商品候補取得
  - ホットペッパーAPI: 飲食店・外食ご褒美候補取得

Nova Act
  - Amazon商品検索（Amazon API代替）
  - 候補プール作成
  - 検証導線あり
  - カート投入・購入操作はやらない
```

LINE Push通知は廃止方向とする。

```text
廃止 / 非推奨:
- LINE Push通知
- LINE Push Scheduler
- LINE Push Queue
- LINE Push Manager

継続:
- LINE BotのReply
- LINE Botのリッチメニュー
- LINE Login
- LINE userIdによるユーザー識別
- PWA Web Push通知
```

# 1. LINE Botを中核に戻す

## 問題

現在、リッチメニューや各会話フローが単発処理になっており、ユーザーの次の発話が「何の続きか」として扱われていない。

その結果、以下が起きている。

```text
リッチメニューから話し始める
↓
リワードちゃんが質問する
↓
ユーザーが答える
↓
文脈が消える
↓
無関係な雑談や別フローに流れる
```

## 修正方針

LINE Botのすべての会話は `CONVERSATION_STATE#CURRENT` を中心に処理する。

```json
{
  "PK": "USER#{lineUserId}",
  "SK": "CONVERSATION_STATE#CURRENT",
  "entityType": "CONVERSATION_STATE",
  "current_flow": "ONBOARDING",
  "step": "WAITING_INCOME",
  "expected_input": "amount",
  "context": {
    "last_question": "毎月の手取り収入を教えてね",
    "last_suggestion": null,
    "source": "line_bot"
  },
  "expires_at": 1760000000
}
```

想定する flow:

```text
ONBOARDING
TALK
EXPENSE_ENTRY
EXPENSE_CONFIRM
REWARD_PROPOSAL
PURCHASE_CONFIRM
PWA_PUSH_SETUP
API_CANDIDATE_REVIEW
NOVA_ACT_REVIEW
NONE
```

LINE Botのテキスト処理順序は以下に固定する。

```text
1. lineUserId を取得
2. CONVERSATION_STATE#CURRENT を取得
3. 状態中なら、そのフローを最優先で処理
4. 状態がなければ intent 分類
5. 支出・嗜好・感情を副作用として抽出
6. 必要に応じてご褒美候補を取得
7. 最後にリワードちゃん口調で返信
```

# 2. リッチメニューを状態開始ボタンにする

## 問題

リッチメニューが単なるショートカットになっている。
これでは次のユーザー発話を文脈として扱えない。

## 修正方針

各リッチメニュー postback で `CONVERSATION_STATE#CURRENT` を作成する。

### 話す

```text
action=start_talk
→ current_flow=TALK
→ step=WAITING_FREE_REPLY
→ expected_input=free_text
```

例:

```text
リワードちゃん：
最近ちょっとハマってるものある？
甘いものでも、飲み物でも、ゲームでもなんでもいいよ。

ユーザー：
抹茶プリンかな

処理:
- PREF_MEMORY# に「抹茶」「プリン」を保存
- TALK状態を完了
```

### 支出登録

```text
action=start_expense
→ current_flow=EXPENSE_ENTRY
→ step=WAITING_EXPENSE_TEXT
→ expected_input=expense_text
```

例:

```text
リワードちゃん：
今日買ったものをそのまま教えて。
「コーヒー150円買った」みたいな感じでOK。

ユーザー：
コーヒー150円買った

処理:
- EXPENSE# 保存
- MONTHLY_SUMMARY# 更新
- 状態完了
```

### ご褒美相談

```text
action=start_reward
→ current_flow=REWARD_PROPOSAL
→ step=WAITING_REWARD_REQUEST
→ expected_input=free_text
```

例:

```text
リワードちゃん：
今日はどんな感じで甘やかされたい？
甘いもの、休憩、癒し、何も考えたくない系、どれでもいいよ。

ユーザー：
甘いもの食べたい

処理:
- PREF_MEMORY# と REWARD_POOL# を参照
- 外部API / Nova Act候補も必要に応じて利用
- 候補提案
- PURCHASE_CONFIRM 状態へ
```

```text
↓
```

```text
・25万円
```

# 4. 支出登録後に無関係な会話へ流れないようにする

## 問題

支出処理後に通常チャットフローへ落ち、無関係な会話が始まる。

## 修正方針

支出処理後は必ず処理を終了する。

```python
if intent == "EXPENSE":
    reply_text, items_to_save = expense_extractor.extract(text, user_id, ddb)

    if reply_text:
        save_expenses(items_to_save)
        update_monthly_summary(user_id, items_to_save)
        append_memory_side_effects(text, items_to_save)

        line_service.reply_message(reply_token, reply_text)
        return
```

LINEの reply token は1回の返信で使い切る前提とし、二重返信を禁止する。

## service-worker.js

```js
self.addEventListener("push", event => {
  const data = event.data ? event.data.json() : {};

  event.waitUntil(
    self.registration.showNotification(data.title || "リワードちゃん", {
      body: data.body || "ちょっと話したいことがあるよ〜",
      icon: "/icons/icon-192.png",
      badge: "/icons/badge-72.png",
      data: {
        url: data.url || "/pwa"
      }
    })
  );
});

self.addEventListener("notificationclick", event => {
  event.notification.close();

  const url = event.notification.data?.url || "/pwa";

  event.waitUntil(
    clients.matchAll({ type: "window", includeUncontrolled: true }).then(clientList => {
      for (const client of clientList) {
        if (client.url.includes("/pwa") && "focus" in client) {
          return client.focus();
        }
      }
      return clients.openWindow(url);
    })
  );
});
```

# 9. 外部API統合・Nova Act Amazon検索統合

## 背景

Auto-Reward-Service では、ユーザーがLINE Bot上でリワードちゃん / ふれまーるちゃんと会話しながら、収入・固定費・支出・好み・疲れ・ご褒美履歴を登録する。

その情報をもとに、外部APIやNova Actを使って商品・飲食店候補を探し、ユーザーに「買っていい理由」「行っていい理由」を提示する。

Amazon Product Advertising API は払い出し・利用条件が重いため、MVPではAmazon APIの代替として Nova Act によるAmazon商品検索を使う。

一方で、楽天APIとホットペッパーAPIは通常の外部APIとして統合する。

## 重要方針

### やること

- 楽天APIで商品候補を取得する
- ホットペッパーAPIで飲食店・ご褒美外食候補を取得する
- Nova ActでAmazonの商品検索・商品情報抽出を行う
- 候補を共通の `RewardCandidate` 形式に正規化する
- 候補を `REWARD_POOL#` に保存する
- LIFFで候補表示と購入・来店導線を提供する

### やらないこと

- Nova ActによるAmazonカート投入
- Nova Actによる購入操作
- Amazonログイン操作
- 保存済みAmazonセッションの利用
- 注文確定
- 決済

## 候補取得の全体構成

```text
商品候補取得
├─ 楽天API
├─ ホットペッパーAPI
├─ Nova Act Amazon検索
├─ キャッシュ済み候補
└─ Static候補

購入導線
├─ Amazon Add-to-Cart URL / 商品URL
├─ 楽天商品URL
├─ ホットペッパー店舗URL / クーポンURL
└─ LINE Botで「買った」「行った」を記録
```

## RewardCandidate Provider構成

```text
src/providers/

  rakuten_reward_provider.py
  hotpepper_reward_provider.py
  nova_act_amazon_search_provider.py
  cached_reward_pool_provider.py
  static_reward_provider.py
```

共通インターフェイス:

```python
class RewardCandidateProvider:
    def search(self, query: str, user_context: dict) -> list[dict]:
        ...
```

Provider優先順位:

```text
1. CachedRewardPoolProvider
2. RakutenRewardProvider
3. HotpepperRewardProvider
4. NovaActAmazonSearchProvider
5. StaticRewardProvider
```

ただし、LIFFや管理画面で「Amazonで探してもらう」を押した場合は、明示的に `NovaActAmazonSearchProvider` を起動できるようにする。

## RewardCandidate 共通Schema

楽天、ホットペッパー、Amazon Nova Act、Static候補をすべて以下の形式に正規化する。

```json
{
  "candidate_id": "string",
  "name": "抹茶プリン",
  "description": "疲れた日の小さなご褒美に合うスイーツ",
  "amount": 320,
  "currency": "JPY",
  "image_url": "https://...",
  "url": "https://...",
  "source": "rakuten|hotpepper|nova_act_amazon|static",
  "source_item_id": "string",
  "asin": "BXXXXXXXXX",
  "shop_name": "string",
  "category": "スイーツ",
  "tags": ["抹茶", "プリン", "スイーツ"],
  "reward_type": "product|restaurant|experience",
  "confidence": 0.82,
  "reason": "今月のご褒美枠に収まり、過去の好みに合うため"
}
```

注意:

* Amazon候補のみ `asin` を持つ
* ホットペッパー候補は `reward_type=restaurant`
* 楽天候補は基本 `reward_type=product`
* ホットペッパーの価格は厳密な商品価格ではなく、予算帯・平均予算・想定利用額として扱う
* URLがある候補は必ずLIFFから開けるようにする


# 10. Nova Act Amazon検索 Provider

## Nova Actでやること

* Amazon.co.jpを開く
* 指定キーワードで商品検索する

* 商品ページを開く
* 商品名、価格、画像URL、商品URL、ASINを抽出する
* `RewardCandidate` に正規化する

## Worker処理フロー

```text
1. DynamoDBから queued ステータスのジョブを取得
2. Nova Actでブラウザを起動（ログイン不要、匿名検索）
3. Amazon.co.jpの検索バーにquery入力
4. 検索結果一覧から候補を抽出
5. 各候補の商品ページを開いて詳細取得
6. 結果をDynamoDBに保存
7. REWARD_POOL# に候補を保存
8. ジョブステータスを completed に更新
```

```text
→ ユーザーには自然な返答
```

# 最終設計思想

ARSの中心はPWAではない。
中心は **LINE Bot上のリワードちゃんとの会話**。

```text
LINE Botで会話する
↓
収入・固定費・支出・好み・疲れが蓄積される
↓
外部API / Nova Act / キャッシュから候補を取得する
↓
予算と好みに合うご褒美を選ぶ
↓
リワードちゃんが「買っていい理由」を返す
↓
買ったらご褒美費として記録する
↓
PWA Web Pushで再訪を促す
↓
またLINE Botで会話する
```

PWAは、LINE Botを置き換えるものではない。
**PWAは通知のための補助装置。**

だから修正の優先順位はこう。

```text
1. LINE Botの会話状態管理
2. リッチメニュー起点の文脈維持
3. 収入・固定費オンボーディング体験改善
4. 支出登録と購入確定の安定化
5. 外部API / Nova Act候補取得のProvider化
6. Nova Act検証導線
7. PWA Web Push購読・通知
8. LINE Push廃止整理
```

これで、ARSは「機能がバラバラにある状態」から、
**LINE Botの会話体験を中心に、PWA通知・外部API・Nova Actが周辺で支える構造**になります。
