## Q1: 音声チャットの実装方式

ふれまーるちゃんとの音声チャットについて、どの方式を採用しますか？

A) **ブラウザ Web Speech API** — STT/TTS をブラウザ側で処理。サーバーにはテキストのみ送信。低コスト・低遅延だが音声品質はブラウザ依存
B) **Amazon Bedrock + Polly/Transcribe** — AWS側でSTT（Transcribe）→ LLM → TTS（Polly）。高品質だがコスト高・遅延あり
C) **OpenAI Realtime API** — WebSocket接続でリアルタイム音声会話。最も自然だが最もコスト高（GPT-4o-realtime等）
D) **ハイブリッド（STTはブラウザ、LLMはBedrock/OpenAI、TTSはPolly or ブラウザ）** — コストと品質のバランス
X) その他（以下に記述）

[Answer]: X
リアルタイム会話は OpenAI Realtime API。
ただし、会話内容の分析・ライフログ化・家計簿更新はリアルタイム処理に含めず、別LLMで非同期実行する。

PWA音声会話では OpenAI Realtime API を使い、自然な会話体験を優先する。
会話Transcriptをバックエンドに保存し、別ジョブで高品質LLMに渡してライフログ・家計簿・ストレス判定・ご褒美提案を生成する。

## Q2: LLMモデル選定

A) **Claude 3.5 Sonnet (Bedrock)** — 高性能・日本語◎・Bedrock経由で統一
B) **Claude 3 Opus (Bedrock)** — 最高性能だが高コスト・低速

E) **用途別に使い分け**（会話: Claude Sonnet / ストレス判定: Nova Pro / 意図分類: Nova Micro 等）

要約・日記サマリ:
- 高品質LLM

ハッカソンなので、コストより体験品質を優先する。

## Q6: ストレス判定のロジック

ストレス度をどのように判定しますか？

A) **会話内容のみ** — ネガティブワード・疲労表現の頻度、感情スコア推移
B) **会話 + 余剰金状況** — 会話のストレスシグナル + 支出パターン（衝動買い傾向等）
C) **会話 + 余剰金 + ライフログ** — B + 運動量低下、外出減少、睡眠不足等の複合判定
D) **LLMに丸ごと判定させる** — 蓄積した全情報をLLMに渡してストレス度とご褒美タイミングを判定
X) その他（以下に記述）

[Answer]:Cで総合的に判断、適切なアドバイスをふれまーるちゃんがくれるといいね
会話 + 余剰金 + ライフログで総合的に判定する。

判定材料:

- 会話中の疲労表現

- 余剰金
- 甘やかし枠の残額
- 運動量
- 外出頻度

- 活動量
- 0円回復の回数
- やけくそ費の有無

## Q7: 商品/サービス誘導の方式

「自然にお金を使ってもいいよという風に誘導する」具体的にどうイメージしていますか？

A) **会話の流れで提案** — ストレス高 + 余剰金ある時、「たまには自分にご褒美あげてもいいんじゃない？」と会話中に提案
B) **ダッシュボード上にカード表示** — ストレス判定結果に基づいてPWA上にご褒美おすすめカードを表示
C) **両方 + ワンタップカート** — 会話で提案 + PWAカード + そのままカート追加（既存Amazon連携活用）
D) **段階的アプローチ** — まず軽い提案（「疲れてるね」）→ 反応見て具体的商品提案 → カート誘導
X) その他（以下に記述）

[Answer]:D
段階的アプローチにする。

いきなり商品やサービスを出すと広告に見えるため、会話の流れで自然に出す。

方針:

1. まず気持ちを受け止める
2. 疲れ・ストレス・余剰金を見て判断する
3. 「少し回復に使ってもよさそう」と伝える
4. 反応があれば具体的な提案をする
5. 商品だけでなく、YouTube動画・記事・休息・0円回復も提案する

文言例:

今日の感じなら、ちょっと回復に使ってもいいかも。

## Q9: PWAのオフライン対応

PWAとして、オフライン時にどの程度動作させますか？

A) **オンライン前提** — ネットワーク必須。Service Worker はキャッシュ目的のみ
B) **会話履歴閲覧のみオフライン** — 過去のチャット/日記はキャッシュで閲覧可能
C) **テキスト入力のみオフライン** — オフライン中の入力をキューイングし、復帰時に送信
D) **最小限のPWA対応** — ホーム画面追加・起動スプラッシュのみ。機能はオンライン必須
X) その他（以下に記述）

[Answer]:A
オンライン前提にする。

理由:

- OpenAI Realtime API
- 高品質LLM分析
- PWA Push
- ダッシュボード更新
- ライフログ保存

がオンライン前提のため。

Service Workerは、静的ファイルのキャッシュやPWA起動体験の改善に使う。
