# ARS 方針まとめ

## 1. コンセプト

ARSは、普通の家計簿アプリではない。

> **頑張ったあなたに、ちょっとだけご褒美を。
> 話すだけで家計簿になり、好きなものを覚えてくれる、頑張りすぎない家計簿アプリ。**

ユーザーは家計簿をつけようと頑張らない。
LINEでリワードちゃんと話すだけ。

* 愚痴る
* 買ったものを話す
* レシート画像を送る
* 好きなものを話す
* 「これ買っていい？」と聞く

すると、裏側で勝手に、

* 支出履歴
* 感情ログ
* ご褒美枠
* 好きな商品カテゴリ
* 買いやすいタイミング
* 購入後の満足/後悔
* ご褒美候補プール

が育っていく。

ARSの本質は、

> **会話の副産物として、家計簿と嗜好データが育つサービス**

です。

---

# 2. 体験の中心はLINE Bot

MVPでは通常のWebアプリは不要。
体験の中心は **LINE Bot**。

## LINEで完結させること

```text
- 初回登録
- 月収・ボーナス・固定費のざっくり登録
- 愚痴チャット
- 支出報告
- レシート画像送信
- 支出登録確認
- ご褒美相談
- 商品提案
- Push通知
```

LINEは、ユーザーが普段使う場所なので、
「家計簿アプリを開く」という面倒を消せる。

---

# 3. ダッシュボードはLIFF

通常のWebダッシュボードは作らない。
必要なら、LINE内で開く **LIFFダッシュボード** にする。

ただし、ユーザーに機械的な数値は見せない。

## 見せない

```text
甘やかされ度：72%
罪悪感軽減率：88%
疲労スコア：81
ご褒美必要度：S
```

こういう表示は冷める。

## 見せるならキャラの言葉

```text
今月はコンビニスイーツ多めだけど、
大きな無駄遣いはまだしてないよ〜。

あと少しなら、甘いもの買っても大丈夫そう。
でもガジェット系は来月まで待と？
```

内部ではスコアリングする。
表にはリワードちゃんの言葉で出す。

---

# 4. リワードちゃんがプロダクトの中心

ARSは機能よりも、**リワードちゃんへの愛着**が大事。

リワードちゃんは、ただのマスコットではなく、

* 初回登録で質問する
* 愚痴を聞く
* 支出を覚える
* レシートを読む
* 好きなものを覚える
* ご褒美を提案する
* 買ったら喜ぶ
* 買わなかったら少し残念そうにする
* 買いすぎそうならやんわり止める

存在。

## 口調例

```text
今日もおつかれ〜。
それはプリン案件かも。

今月まだちょっと余裕あるよ。
これ買っちゃおうよ〜。

これは浪費じゃなくて、回復費でいけるやつ！
```

---

# 5. キャラの性格は変えない。口調だけ変える

ユーザーがカスタムできるのは、**性格ではなく口調**。

## 固定するもの

```text
- ユーザーを肯定する
- 頑張りすぎない方向へ寄せる
- 小さなご褒美を提案する
- 買いすぎはやんわり止める
- 家計簿を感じさせずに記録する
- 好きなものを覚える
- 数字やスコアを機械的に見せない
```

## 変えられるもの

```text
- フレンドリー
- やさしい敬語
- 小悪魔
- お姉さん
- ゆるふわ
```

判断基準は変えない。
**同じ判断を、違う話し方で返す**。

---

# 6. 初回登録はチャットで行う

フォーム入力や金融連携は重い。
初回登録はリワードちゃんがチャットで聞く。

```text
リワードちゃん：
まずざっくり教えて〜。
毎月の手取りってどれくらい？
だいたいでいいよ、だいたいで！

ユーザー：
30万くらい。ボーナスは年2回で合計80万。

リワードちゃん：
おっけ〜。
家賃とか固定費もざっくり教えて〜。

ユーザー：
家賃8万、スマホ1万、光熱費2万、サブスク5000円くらい。

リワードちゃん：
ありがと〜。
じゃあ今月のごほうび枠、まず2万円くらいから始めよっか。
```

CSV連携・銀行API連携はFuture。
MVPではやらない。

---

# 7. 家計簿入力は「チャット」と「画像」

## チャット入力

```text
今日セブンでプリンとカフェラテ買った。たぶん900円くらい。
```

ARSが裏で、

```json
{
  "item": "プリン、カフェラテ",
  "amount": 900,
  "normalCategory": "食費",
  "arsCategory": "情緒安定費"
}
```

として登録候補を作る。

## 画像入力

レシート画像や注文履歴スクショをLINEで送る。

```text
セブンイレブン 1,280円っぽいね。
プリンとカフェラテとからあげかな。

これは緊急回復費で覚えていい？
```

画像解析後はJSON化して保存し、同じ画像を再解析しない。

---

# 8. 追加質問で自然に登録精度を上げる

ユーザーが、

```text
プリン買った
```

だけ言った場合、リワードちゃんが自然に聞く。

```text
やった〜。それは情緒安定費で覚えたい。
いくらだった？あと、なんてプリン？
次に似たやつ見つけたい〜
```

ユーザーが、

```text
320円の濃厚たまごプリン
```

と答える。

リワードちゃんは、

```text
濃厚たまごプリン、320円ね。覚えた〜。
今日はそれ、必要なやつだったよ。

たまご系プリン、次も見張っとく。
```

のように返す。

## 出さない

```text
今日の記録：
・濃厚たまごプリン
・320円
・情緒安定費
・疲れた日の小さめご褒美
```

こういう構造化表示は出さない。
ユーザーには「覚えてくれた感」だけ出す。

---

# 9. ご褒美候補プールを育てる

ARSは、毎回リアルタイムに商品を探すのではない。
ユーザーごとに **ご褒美候補プール** を育てる。

## 候補プールに入るもの

* ユーザーが好きそうな商品
* 過去に買った商品と近いもの
* 好きなカテゴリ
* 低価格ご褒美
* 新商品
* 提携商品
* スルーされにくい商品
* 疲れた日に効きそうな商品

## 例

ユーザーが、

* 抹茶が好き
* コンビニスイーツをよく買う
* 金曜夜に買いやすい
* 疲れた日に甘いものを欲しがる

なら、候補プールに、

```text
抹茶プリン
カフェラテ
入浴剤
低価格スイーツ
```

などを貯める。

---

# 10. 今の状態に近い候補を出す

ユーザーが、

```text
今日疲れた
```

と言ったら、リアルタイムで商品検索しない。

その時点の状態を見て、

```text
- 疲労
- 小さめご褒美
- 今月まだ余裕あり
- 甘いもの欲求あり
```

候補プールから近い商品を選ぶ。

返答は、

```text
前に抹茶好きって言ってたよね〜。
今日ならこの抹茶プリン、ちょうどいいかも。
320円だし、これは回復費でいけるよ。
```

これがARSらしい。

---

# 11. 日次バッチは「今日のおすすめ」ではなく候補プール更新

日次バッチでユーザーごとの「今日の1個」を作るのではなく、
**候補プールを更新する**。

## バッチの役割

```text
- 商品マスタを見る
- ユーザーの好みと照合する
- 候補プールに追加する
- 古い候補を消す
- 最近スルーされた商品を下げる
- 購入された系統を上げる
- 提携商品を混ぜる
```

LINE会話時は、

```text
今の状態を抽出
↓
候補プールから近いものを選ぶ
↓
キャラ口調で提案
```

---

# 12. Push通知は1日1回まで

Push通知は通数課金対象になるため、基本は1日1回。
通常のユーザー起点会話はReply中心。

## Pushの役割

Pushは売り込み本体ではなく、入口。

```text
今日ちょっとだけ話したいことある〜。
たぶん好きなやつ見つけた。
見る？
```

ユーザーが反応したら、Replyで会話を続ける。

# 14. モデル選定

コストを考えると、Nova中心が良い。

## 推奨

```text
通常会話：Nova Micro
構造化JSON作成：Nova Micro
支出抽出：Nova Micro
画像解析：Nova Lite
キャラ品質が足りない時：Haiku
深い振り返り：Haiku / Sonnet
```

ARSはキャラ品質が命なので、Novaの口調が弱ければ重要応答だけHaikuに逃がす。

# 15. DynamoDB登録用JSON

LLMには直接DynamoDB操作させない。

```text
ユーザー発話
  ↓
Nova
  ↓
構造化JSON
  ↓
Lambdaでバリデーション
  ↓
DynamoDB保存
```

## 保存する主なデータ

```text
- user_profile
- fixed_costs
- chat_logs
- life_logs
- pending_expense
- expenses
- preference_memory
- reward_pool
- reward_suggestions
```

重要情報は確認を挟む。
信頼度が低い場合も確認。

# 16. コスト方針

Nova前提なら、かなり広めに使える。

## 方針

```text
通常会話：1ユーザー1日50〜100会話
画像解析：標準5枚、上位20枚
Push通知：1日1回
深い分析：制限あり
```

画像解析は、処理が1分以内ならReplyで返せる。
1分を超える場合はPushになりがちなので、可能なら「結果を見る」ボタンでユーザー起点に戻す。

# 17. 制限時の見せ方

テンプレ返信はNG。
世界観が壊れる。

ただし制限到達時だけ、キャラの退場演出を複数用意する。

```text
今日はいっぱい話したね〜。
リワードちゃん、そろそろ寝るね。
続きは明日、また聞かせて？
```

```text
今日はもう候補いっぱい出しちゃった。
これ以上すすめると、ほんとに全部買わせちゃいそうだから今日はここまで〜。
明日また見よ？
```

```text
今日はレシートいっぱい見たね〜。
リワードちゃん、目がしょぼしょぼしてきた。
次のレシートは明日見せてね。
```

「制限です」とは言わない。
キャラの都合で自然に閉じる。

# 18. 収益モデル

ARSはアフィリエイトと相性が良い。

## 収益候補

```text
- アフィリエイト
- 提携商品
- クーポン
- スポンサーご褒美
- プレミアム課金
```

ただしPR/アフィリエイト表示は必要。
ユーザーに広告と分からない形は危険。

ARSのダークさは、

> 家計簿なのに、節約させない。
> 買っていい理由を作るほど、ARSが儲かる。

という構造にある。

# 19. ARSの強いところ
ARSは、

> 家計管理・自己制御・消費判断をAIとキャラに溶かされる

という生活密着型の強さがある。

つまり、

ARS = サービスとして強くなりそう

---

# 20. 最終的な一言

ARSはこういうサービス。

> **LINEでリワードちゃんと話しているだけで、
> 愚痴・支出・好み・ご褒美履歴が勝手に記録される。**
>
> **ユーザーは家計簿を頑張らない。
> でも気づいたら、自分の消費傾向が整理されている。**
>
> **そしてリワードちゃんは、ユーザーの好きなものや今月の余裕を覚えて、
> ちょうど弱っているタイミングで、
> 「これ買っちゃおうよ〜」と財布をゆるめてくる。**

短く言うなら、

> **話すだけで家計簿になる。
> 好きなものを覚えて、買っていい理由をくれる。
> 頑張りすぎない家計簿アプリ「ARS」。**
