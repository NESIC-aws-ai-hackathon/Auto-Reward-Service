## 1. エレベーターピッチ

> ストレスを感じた瞬間、財務状況を自動分析してあなたに最適なご褒美を提案する AI サービス。
> 「買っていいよ」の一言を、自分の代わりに AI が言ってくれる。

---

## 2. 問題定義

### 現状の課題

| # | 課題 | 影響 |
|---|------|------|
| 1 | 頑張っても自分にご褒美をあげるタイミングがわからない | 燃え尽き・モチベーション低下 |
| 2 | 「買っていいか」の判断に認知負荷がかかる | 衝動買いまたは過剰な節制 |
| 3 | 家計簿は「記録」するだけで行動を促さない | 財務ツールが受動的にしか機能しない |
| 4 | ストレス発散のための支出が罪悪感と結びつきやすい | 精神的な疲弊の悪化 |

### ユーザーが本当に欲しいもの

- **許可**：「今これを買っても大丈夫」という客観的な安心感
- **提案**：自分の好みに合ったご褒美アイデア（考えなくてよい）
- **自動化**：ストレスピーク時にタイムリーに動いてくれる仕組み

## 3. ビジネス意図（Business Intent）

### ミッション

「頑張る人が、適切なタイミングで適切なご褒美を受け取れる世界を実現する」

### ビジョン

2027 年までに、日本国内の勤労世代（25〜45 歳）に対して、
月 1 回以上の「AI 承認ご褒美体験」を提供する家計管理プラットフォームになる。

### 収益モデル（Revenue Model）

| モデル | 詳細 |
|--------|------|
| サブスクリプション | 月額 ¥480（ベーシック）/ ¥980（プレミアム） |
| アフィリエイト / 送客手数料 | ご褒美提案からの EC・デリバリー・体験予約への送客 |
| データインサイト販売（匿名集計）| ストレスパターン×消費傾向の企業向けレポート |

### KPI（Key Performance Indicators）

| フェーズ | 指標 | 目標値 |
|----------|------|--------|
| MVP（3 ヶ月） | DAU | 500 人 |
| MVP（3 ヶ月） | リワード提案→実行転換率 | 30 %以上 |
| Growth（6 ヶ月） | MAU | 10,000 人 |
| Growth（6 ヶ月） | 月次チャーン率 | 5 %以下 |
| Scale（12 ヶ月） | ARR | ¥50M |

## 5. スコープ

### In Scope（Inception フェーズ）

- ストレス度の推定ロジック設計
- 財務余裕額算出ロジック設計
- リワード提案エンジン（ルールベース → AI 強化）
- モバイルアプリ（iOS / Android）の UI/UX 設計
- 家計連携 API（銀行・クレカ口座）との接続設計

### Out of Scope（将来フェーズ）

- 完全自動決済・購入実行（フェーズ 2 以降）
- ウェアラブルデバイスとの直接連携（フェーズ 3 以降）
- 海外展開・多通貨対応

## 6. 成功シナリオ

> ユーザーの佐藤さん（32 歳、会社員）は月曜の残業後、
> スマホに「今日は頑張りましたね。残高余裕は ¥3,200 です。
> 近くのラーメン店で一杯いかがですか？🍜」と通知が届く。
> タップ一つで予約完了。翌朝は「昨夜の支出 ¥850 を記録しました」と報告される。

## 7. リスクと対策

| リスク | 深刻度 | 対策 |
|--------|--------|------|
| ストレス推定精度が低い | 高 | 複数シグナルのアンサンブル＋ユーザーフィードバックループ |
| 金融 API との連携コスト | 中 | 当初は手動入力 or CSVインポートで代替、API は段階導入 |
| 過剰消費を助長するリスク | 高 | 月次予算上限の設定・支出警告機能を必須実装 |
| ユーザーのプライバシー懸念 | 高 | データは端末内処理優先、サーバー送信は最小化・暗号化 |

## 8. ペルソナ

### Persona A — 佐藤 健太（32 歳・営業職）

> 月末になると残業が続き、ストレスが溜まる。
> たまにはご褒美を買いたいけど、「使いすぎかな…」と罪悪感が出て踏み切れない。
> 家計簿は続いたことがない。

### Persona B — 田中 美咲（28 歳・エンジニア・フリーランス）

> 収入が不安定で財布の紐が固い。
> ストレスを感じてもご褒美への「お金の許可」が自分では出せない。
> データに基づいた客観的な判断が欲しい。

### Persona C — 山田 さくら（35 歳・育児中・パート）

> 家事・育児・仕事の三足のわらじで慢性的に疲弊。
> 夫や子供のことを優先しすぎて自分へのご褒美は後回し。
> 手間をかけずに「今日の小さな幸せ」を提案してほしい。

### E1: ユーザーオンボーディング

**US-01**
```
As a 新規ユーザー
I want to メールまたは Google アカウントで 30 秒以内に登録できる
So that すぐにサービスを使い始められる
```
受入基準:
- [ ] メール + パスワードでアカウント作成できる
- [ ] Google OAuth でワンタップ登録できる
- [ ] 登録完了後、初期設定ウィザードに遷移する

**US-02**
```
As a 新規ユーザー
I want to 好みのご褒美カテゴリと月次ご褒美予算を設定できる
So that 自分に合った提案が最初から届く
```
受入基準:
- [ ] ご褒美カテゴリ（食・体験・物・サービス）を複数選択できる
- [ ] 月次ご褒美予算上限を ¥500 刻みで設定できる
- [ ] 後から設定変更できる

### E2: ストレス記録

**US-03**
```
As a ユーザー
I want to 今日のストレスを 5 段階で素早く入力できる
So that アプリが私のストレス状態を把握してくれる
```
受入基準:
- [ ] ホーム画面から 2 タップ以内でストレス入力ができる
- [ ] 入力にかかる時間は 10 秒以内
- [ ] 入力後に「記録しました」の確認フィードバックが表示される

**US-04**
```
As a ユーザー
I want to Google カレンダーと連携してストレス推定を自動化できる
So that 毎日手動入力しなくてもよくなる
```
受入基準:
- [ ] Google OAuth でカレンダーの読み取り権限を要求する
- [ ] 予定の密度・深夜予定・連続稼働日数を自動スコアリングする
- [ ] 自動スコアは手動入力で上書きできる

**US-05**
```
As a ユーザー
I want to ストレスが一定レベルを超えたら即座に通知を受け取りたい
So that 自分がストレスピーク状態にあることに気づける
```
受入基準:
- [ ] ストレススコアが設定閾値（デフォルト 70）を超えたらプッシュ通知が来る
- [ ] 通知はサイレント時間帯（デフォルト 22:00〜7:00）には来ない
- [ ] 通知内にリワード提案へのディープリンクが含まれる

### E3: 財務設定・管理

**US-06**
```
As a ユーザー
I want to 月収と固定費を手入力して財務状況を登録できる
So that アプリが余裕額を計算できる
```
受入基準:
- [ ] 月収・固定費（家賃・保険・サブスクなど）を項目別に入力できる
- [ ] 入力値から当月余裕額がリアルタイムに表示される

**US-07**
```
As a ユーザー
I want to 銀行の明細 CSV をアップロードして自動で収支を取り込みたい
So that 手入力の手間を省ける
```
受入基準:
- [ ] 主要銀行（三菱 UFJ・三井住友・ゆうちょ）の CSV フォーマットに対応
- [ ] 取り込んだ明細は AI で自動カテゴリ分類される
- [ ] 誤分類はユーザーが手動修正できる

### E4: リワード提案受け取り

**US-08**
```
As a ストレスが高まっているユーザー
I want to 財務状況に見合ったご褒美を自動提案してもらいたい
So that 罪悪感なく「今日のご褒美」を決められる
```
受入基準:
- [ ] ストレス閾値超過から 60 秒以内に提案通知が届く
- [ ] 提案は余裕額内に収まる価格帯のものだけが表示される
- [ ] 提案は 3 件以上表示される

**US-09**
```
As a ユーザー
I want to 近くの店舗・サービスのご褒美を優先的に提案されたい
So that すぐに実行に移せる
```
受入基準:
- [ ] 位置情報を許可すると半径 2km 以内の店舗が優先表示される
- [ ] 位置情報なしでも提案は届く（オンラインサービス・デリバリーを優先）

**US-10**
```
As a ユーザー
I want to 気分に合わないご褒美を「却下」してフィードバックできる
So that 次回以降の提案精度が上がる
```
受入基準:
- [ ] 「採用」「後で」「却下」の 3 択フィードバックが選べる
- [ ] 却下理由（高すぎる・カテゴリが違う・気分じゃない）を選択できる
- [ ] フィードバックは次回提案の重み付けに反映される

### E5: リワード実行・フィードバック

**US-11**
```
As a ユーザー
I want to 提案されたご褒美を採用したら自動で家計簿に記録されてほしい
So that 別途入力する手間がない
```
受入基準:
- [ ] 「採用」タップ時に金額・カテゴリが自動記録される
- [ ] 実際の支出額はあとから編集できる

### E6: 振り返り・インサイト

**US-12**
```
As a ユーザー
I want to 先月のストレスとご褒美の関係をグラフで確認したい
So that 自分のパターンを理解して将来の予算計画に活かせる
```
受入基準:
- [ ] ストレス推移（折れ線）とご褒美支出（棒グラフ）が同軸で表示される
- [ ] 月次・週次の切り替えができる

**US-13**
```
As a ユーザー
I want to 「あなたはストレスが高い火曜夜にスイーツを選ぶ傾向がある」
         のような AI インサイトを受け取りたい
So that 自己理解が深まり次のご褒美計画に活かせる
```
受入基準:
- [ ] 月 1 回、AI 生成のインサイトレポートが配信される
- [ ] レポートはポジティブなトーンで、自己批判的な内容を避ける

## 10. Unit 分解

### Unit 一覧

```
オートリワードサービス
├── U1: ユーザー管理
├── U2: ストレスセンシング
├── U3: 財務状況分析
├── U4: リワード提案エンジン
├── U5: 通知・配信
├── U6: リワード実行（将来）
└── U7: 振り返りダッシュボード
```

### U1: ユーザー管理

**責務**: アカウント・プロフィール・設定の管理

| 機能 ID | 機能名 | 優先度 | 説明 |
|---------|--------|--------|------|
| U1-01 | 新規登録・ログイン | Must | メール / SNS 認証 |
| U1-02 | プロフィール設定 | Must | 名前・年齢・職種・ライフスタイル |
| U1-03 | 嗜好設定 | Must | 好きなご褒美カテゴリ（食・体験・物・サービス） |
| U1-04 | 予算上限設定 | Must | 月次ご褒美予算の上限金額 |
| U1-05 | 通知設定 | Should | プッシュ通知の受信時間帯・頻度 |
| U1-06 | データエクスポート | Could | 個人データの CSV/JSON ダウンロード |

**依存**: なし
**境界**: 認証トークン発行まで。財務・ストレスデータの保持は各 Unit が担当。

### U2: ストレスセンシング

**責務**: ユーザーのストレス度をリアルタイムに推定しスコア化する

| 機能 ID | 機能名 | 優先度 | 説明 |
|---------|--------|--------|------|
| U2-01 | 手動ストレス入力 | Must | 1〜5 段階のセルフ評価入力 |
| U2-02 | カレンダー連携 | Should | Google / Apple Calendar から予定密度を取得 |
| U2-03 | テキスト感情分析 | Should | 日記・メモ入力から LLM で感情スコアを算出 |
| U2-04 | 活動量連携 | Could | ヘルスケアアプリ（歩数・睡眠）からバイタル取得 |
| U2-05 | ストレス総合スコア算出 | Must | 上記シグナルを重み付け合成しスコア 0〜100 を生成 |
| U2-06 | ストレス閾値判定 | Must | 設定閾値超過時にイベントを発火 |
| U2-07 | ストレス履歴保存 | Must | 時系列でスコアを記録 |

**依存**: U1（ユーザー ID）
**境界**: ストレスイベント（`stress.threshold_exceeded`）の発火まで。

#### ストレス総合スコア算出ロジック（概要）

```
stress_score = w1 * manual_input
             + w2 * calendar_density_score
             + w3 * text_sentiment_score
             + w4 * (1 - sleep_quality_score)

デフォルト重み: w1=0.4, w2=0.2, w3=0.3, w4=0.1
```

### U3: 財務状況分析

**責務**: ユーザーの現在の財務状況から「リワードに使える余裕額」を算出する

| 機能 ID | 機能名 | 優先度 | 説明 |
|---------|--------|--------|------|
| U3-01 | 手動収支入力 | Must | 収入・固定費の手動登録 |
| U3-02 | CSV インポート | Should | 銀行・クレカの明細 CSV 取り込み |
| U3-03 | 家計 API 連携 | Could | Moneytree / マネーフォワード API 経由での自動取得 |
| U3-04 | 月次予算管理 | Must | カテゴリ別の月次予算設定と実績管理 |
| U3-05 | 余裕額算出 | Must | `余裕額 = 月次ご褒美予算上限 - 今月のご褒美累計支出` |
| U3-06 | 支出カテゴリ分類 | Should | AI で明細を自動カテゴリ分類 |
| U3-07 | 財務健全性スコア | Could | 貯蓄率・負債比率から総合財務スコアを算出 |

**依存**: U1（ユーザー ID）
**境界**: 余裕額（`available_reward_budget`）の提供まで。

#### 余裕額算出ロジック（概要）

```
available_reward_budget =
  min(
    monthly_reward_limit,
    (monthly_income - monthly_fixed_expenses) * safety_factor
  ) - current_month_reward_spent

safety_factor = 0.15  # 収支差の最大 15% をリワード枠とする
```

### U4: リワード提案エンジン

**責務**: ストレススコアと財務余裕額からパーソナライズされたご褒美を提案する

| 機能 ID | 機能名 | 優先度 | 説明 |
|---------|--------|--------|------|
| U4-01 | リワードカタログ管理 | Must | カテゴリ・価格帯・地域のご褒美マスタデータ |
| U4-02 | ルールベース提案 | Must | 余裕額×ストレスレベル→価格帯・カテゴリのマッピング |
| U4-03 | AI パーソナライズ | Should | 過去の選択履歴から嗜好モデルを学習し提案精度を向上 |
| U4-04 | ロケーションベース提案 | Should | 現在地近辺の店舗・サービスを優先表示 |
| U4-05 | 提案フィードバック収集 | Must | 「採用」「却下」「後で」のリアクション収集 |
| U4-06 | 季節・トレンド反映 | Could | 旬のイベント・セール情報を提案に組み込む |

**依存**: U2（ストレススコア）、U3（余裕額）、U1（嗜好設定）
**境界**: リワード提案リスト（`reward_proposals[]`）の生成まで。

#### 提案マトリクス（ルールベース）

| ストレスレベル | 余裕額 | 提案カテゴリ例 | 価格帯目安 |
|--------------|--------|--------------|-----------|
| 高（70〜100） | ¥5,000 以上 | スパ・エステ・高級ディナー | ¥3,000〜¥8,000 |
| 高（70〜100） | ¥500〜¥4,999 | スイーツ・ちょっといい外食 | ¥500〜¥2,000 |

**責務**: ストレスイベント発火時に適切なタイミングでユーザーへ提案を届ける

## 11. システムアーキテクチャ

### アーキテクチャ概要

オートリワードサービスは **イベント駆動マイクロサービス** アーキテクチャを採用します。
各 Unit が独立したサービスとして動作し、メッセージブローカーを介して非同期に連携します。

```
┌─────────────────────────────────────────────────────────────────┐
│                          クライアント層                           │
│   iOS App (Swift)    Android App (Kotlin)    Web App (React)     │
└──────────────────────────────┬──────────────────────────────────┘
                               │ HTTPS / WebSocket
┌──────────────────────────────▼──────────────────────────────────┐
│                         API Gateway                              │
│          (認証・レートリミット・ルーティング)                        │
└────┬──────────┬──────────┬──────────┬──────────┬───────────────┘
     │          │          │          │          │
     ▼          ▼          ▼          ▼          ▼
 [Auth     [Stress    [Finance   [Reward    [Notif
 Service]  Service]   Service]  Service]  Service]
     │          │          │          │          │
     └──────────┴──────────┴────┬─────┴──────────┘
                                │
                    ┌───────────▼───────────┐
                    │   Message Broker       │
                    │   (Apache Kafka)       │
                    └───────────────────────┘
                                │
                    ┌───────────▼───────────┐
                    │   Dashboard Service    │
                    │   (集計・分析)          │
                    └───────────────────────┘
```

### サービス構成

| サービス | 対応 Unit | 役割 | 技術スタック |
|---------|----------|------|------------|
| Auth Service | U1 | 認証・認可・プロフィール管理 | Node.js + TypeScript, PostgreSQL |
| Stress Service | U2 | ストレス度の収集・スコアリング・イベント発火 | Python + FastAPI, TimescaleDB |
| Finance Service | U3 | 収支管理・余裕額算出 | Python + FastAPI, PostgreSQL |
| Reward Service | U4 | リワード提案の生成・管理 | Python + FastAPI, PostgreSQL, Redis |
| Notification Service | U5 | プッシュ通知・インアプリ通知の配信 | Node.js + TypeScript |
| Dashboard Service | U7 | データ集計・ダッシュボード API 提供 | Python + FastAPI, ClickHouse |

### データフロー（ストレス検知→通知）

```
1. ユーザーがストレス入力 or カレンダー同期
       │
       ▼
2. Stress Service がスコアを算出
   → score >= threshold の場合
       │
       ▼
3. Kafka: stress.threshold_exceeded イベント発行
   payload: { user_id, stress_score, timestamp }
       │
       ▼
4. Finance Service: 余裕額を算出
   → finance.budget_available イベント発行
   payload: { user_id, available_budget }
       │
       ▼
5. Reward Service: 提案リストを生成
   → reward.proposals_ready イベント発行
   payload: { user_id, proposals: [...] }
       │
       ▼
6. Notification Service: 通知コピーを生成して Push 送信
```

### インフラ構成

**MVP（ハッカソン・PoC 環境）**

- Render.com / Railway で各マイクロサービスをコンテナデプロイ
- PostgreSQL Managed / Redis Managed

**本番（スケール後）**

- AWS EKS（Kubernetes）でマイクロサービス管理
- Amazon MSK（Managed Kafka）
- RDS PostgreSQL + ElastiCache Redis
- CloudFront + S3（静的アセット）
- AWS WAF + Shield（DDoS 対策）

## 13. データモデル

### ER 図（概念モデル）

```
users
  ├── id (PK)
  ├── email
  ├── display_name
  ├── preferences (JSONB)   ← 嗜好カテゴリ・通知設定
  ├── created_at
  └── updated_at

stress_entries
  ├── id (PK)
  ├── user_id (FK → users)
  ├── score (0-100)
  ├── source (enum)
  ├── note (text, nullable)
  ├── threshold_exceeded (bool)
  └── recorded_at

finance_budgets
  ├── id (PK)
  ├── user_id (FK → users)
  ├── month (YYYY-MM)
  ├── monthly_income
  ├── fixed_expenses (JSONB)   ← 項目別固定費
  ├── monthly_reward_limit
  └── created_at

transactions
  ├── id (PK)
  ├── user_id (FK → users)
  ├── amount
  ├── category (enum)
  ├── is_reward (bool)
  ├── related_proposal_id (FK → reward_proposals, nullable)
  ├── description (text)
  └── transacted_at

reward_proposals
  ├── id (PK)
  ├── user_id (FK → users)
  ├── stress_entry_id (FK → stress_entries)
  ├── title
  ├── description
  ├── category (enum)
  ├── estimated_price
  ├── location (JSONB, nullable)
  ├── tags (text[])
  ├── confidence_score (float)
  ├── status (enum: pending | accepted | deferred | rejected)
  ├── rejection_reason (enum, nullable)
  └── generated_at

reward_feedbacks
  ├── id (PK)
  ├── proposal_id (FK → reward_proposals)
  ├── action (enum)
  ├── actual_price (nullable)
  └── created_at
```

### 主要な列挙型（Enum）

```typescript
// ストレス入力ソース
type StressSource = "manual" | "calendar" | "text_analysis" | "health_kit";

// リワードカテゴリ
type RewardCategory =
  | "food"        // 食事・グルメ
  | "sweets"      // スイーツ・カフェ

  | "too_expensive"

  | "not_in_mood"
  | "already_done"

type TransactionCategory =
  | "food"
  | "entertainment"
  | "shopping"
  | "self_care"
  | "transport"
  | "utility"
  | "other";
```

## 16. セキュリティ設計

| 観点 | 対策 |
|------|------|
| 通信 | 全通信 TLS 1.3 必須 |
| 認証 | JWT + リフレッシュトークンローテーション |
| 金融データ | AES-256 暗号化 at rest、口座番号マスク |
| 個人データ | GDPR / 個人情報保護法準拠、データ最小化原則 |
| AI 入力 | ユーザーのプライベートテキストはサーバー送信前に匿名化 |
| 依存関係 | 定期的な脆弱性スキャン（Dependabot + Snyk） |
